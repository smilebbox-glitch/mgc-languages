# User Guide — Engineering UI v5.2.0

Интерфейс предназначен только для авторизованных инженеров. AI/RAG/VLM и инфраструктурные термины скрыты из основной работы.

## Вход

Откройте внутренний адрес сервиса и войдите через корпоративный SSO. Если учётная запись не входит в разрешённую инженерную группу, сервис покажет **«Доступ только для инженеров»** и не откроет AI/CAD функции.


## Производственная зона

В верхней части интерфейса есть один переключатель **«Зона»**. Выберите `Все зоны`, `Сварка`, `Окраска`, `Сборка`, `Компоненты`, `Логистика`, `Качество` или другую доступную зону. Выбор автоматически применяется к спискам документов/деталей, проверкам и AI-поиску.

Если файл загружается при выбранной зоне, сервис назначает её автоматически. В карточке документа зону можно изменить. **Общий документ** используется на уровне проекта и не считается принадлежащим отдельному цеху.

В Project Workspace переключатель зон показывает readiness, блокеры, ECR/ECO, milestones и короткий automotive checklist только для выбранного контекста.


## Производственный процесс

Внутри проекта есть одна сворачиваемая карточка **«Производственный процесс»**. Она показывает линию, станцию и операцию только в выбранной производственной зоне. По умолчанию карточка свернута и не перегружает рабочий экран.

После раскрытия инженер может связать операцию с рабочей инструкцией, PFMEA, Control Plan, специальными характеристиками, технологическими параметрами, оснасткой/оборудованием и дефектом/8D. Просроченная калибровка измерительного средства или critical/high дефект без 8D показываются как блокеры для проверки.

Сервис **не является MES/SCADA**: он не запускает оборудование и не отправляет команды в PLC/роботы/контроллеры. Все оценки readiness остаются рекомендательными.

## Engineering Digital Thread

В Project Workspace есть одна сворачиваемая карточка **Engineering Digital Thread**. В свернутом состоянии она показывает только связанность, количество узлов/связей и trace gaps.

Нажмите **«Исследовать»**, затем выберите:

- **Весь проект** — чтобы посмотреть доступные инженерные домены проекта;
- конкретную **деталь** — чтобы получить её локальный impact-thread;
- глубину **1–5** — насколько далеко проходить по явным связям.

Explorer связывает доступные BOM, документы/CAD, требования/V&V, операции, поставщиков, engineering cost, ECR/ECO, замечания, архитектуру/интерфейсы, варианты автомобиля и release baselines. Блок **«Цепочки влияния»** объясняет путь от выбранной детали к связанному объекту. **Trace gaps** показывают отсутствующие связи/evidence, но сервис не придумывает их автоматически.

Explorer работает без GPU и не зависит от генеративной модели. Его процент связанности — справочный показатель полноты цифрового потока и не является Release Readiness или разрешением на выпуск.

## 1. Главная

Четыре обычных действия:

- **Найти информацию** — задать инженерный вопрос;
- **Открыть деталь** — увидеть ревизии, BOM, документы и замечания;
- **Проверить чертёж** — разобрать drawing и связать размеры с STEP;
- **Посмотреть замечания** — увидеть только то, что требует внимания.

## Engineering Change Intelligence v5.1

В проекте под Engineering Digital Thread находится одна сворачиваемая карточка **Engineering Change Intelligence · v5.1**.

Основные действия:
1. Просмотреть **Action Queue** — что требует внимания сейчас.
2. Оценить **Traceability Coverage** и weakest area.
3. В **Change Impact Simulator** выбрать деталь и задать только реально меняющиеся поля. Симуляция ничего не записывает в ECR/ECO/PLM/ERP.
4. Проверить impacted domains, stale/review evidence, действия и цепочки **Почему это затронуто?**.
5. Открыть **Variant Impact Matrix** и влияние по цехам.
6. В **Ask Digital Thread** задавать вопросы по выбранной детали: ответ объединяет детерминированные graph facts и доступные RAG sources.

`STALE` означает детерминированно устаревший snapshot/evidence; `REVIEW_REQUIRED` означает, что автоматическая инвалидизация была бы слишком сильным выводом и требуется инженер.


## Engineering Knowledge Memory v5.2

Под Change Intelligence находится карточка **Engineering Knowledge Memory · v5.2**. Она отвечает на вопрос: «сталкивались ли мы раньше с похожим изменением или дефектом и что тогда произошло?».

- выберите текущий проект или **все доступные проекты**;
- при необходимости выберите деталь;
- введите инженерное описание проблемы;
- смотрите процент похожести и блок **почему похоже**;
- проверяйте сохранённые решение, outcome и evidence;
- recurrence signal означает только необходимость проверить повторяемость, а не автоматически найденную root cause.

Кейс можно сохранить как **Lessons Learned**. Сначала это `DRAFT`. Только Engineering Admin может отметить урок как `VALIDATED`, причём должен быть явно зафиксирован результат и effectiveness. Даже validated lesson остаётся рекомендацией для инженерного анализа, а не автоматическим approval.

## 2. Спросить ИИ

Пишите вопрос обычным языком. Ответ показывает внутренние evidence sources. Если документ использовался в ответе, обращение автоматически появляется в его истории.

## 3. Детали

Карточка детали содержит:

- текущую ревизию;
- историю ревизий;
- BOM;
- связанные документы;
- замечания;
- сравнение ревизий.

Кнопка **«Полная проверка конструкции»** автоматически собирает CAD + drawing + BOM + предыдущую ревизию + Drawing↔3D + validation/VLM сигналы и показывает:

- риск 0–100;
- простой checklist;
- найденные проблемы;
- что инженеру проверить дальше.

Система не утверждает конструкцию вместо инженера.

## 4. Документы

Для чертежа основные действия:

1. **Разобрать чертёж**;
2. **Связать с 3D**;
3. **Проверить изображение ИИ**.

Для STEP/STP используйте **Найти похожие 3D**.

### КОМПАС-3D / T-FLEX CAD

Для `.m3d/.a3d/.t3d/.cdw/.frw/.spw/.kdw/.grb` нажмите **Подготовить для анализа**. Сервис сам выбирает разрешённый локальный CAD gateway, сохраняет оригинал неизменным и создаёт STEP/PDF/DXF derivative.

### Чертёж ↔ 3D

- `✓` — найден один однозначный CAD-кандидат;
- `?` — несколько одинаковых кандидатов, нужно подтверждение;
- `!` — совпадение не найдено.

### История работы

В карточке документа находится **«История работы с документом»**. Там видно:

- кто и когда открывал документ;
- какие вопросы задавались AI по нему;
- кто запускал анализ/сравнение/Design Review;
- что было сделано инженером;
- решения и комментарии;
- статус целостности журнала.

Можно добавить короткую запись: **Что сделано / Проверка / Решение / Вопрос / Другое**. Старые записи через пользовательский API не редактируются.

## 5. Проверки

Здесь показываются открытые инженерные замечания понятным языком. Инженер может отметить замечание как принятое в работу или закрытое; изменение также попадает в историю связанных документов.

## 6. Для IT

Раздел **«Для IT»** видит только `engineering-ai-admins`. Обычный инженер его не видит.

## Принципы интерфейса

- пять основных разделов без инфраструктурного жаргона;
- одно понятное главное действие на задачу;
- источник рядом с выводом;
- неопределённость показывается явно;
- технические детали скрыты по умолчанию;
- AI не подменяет инженерное утверждение;
- desktop и mobile/tablet navigation.


## Инженерные изменения

Откройте **Изменения** → **Создать ECR**. Укажите деталь, исходную/новую ревизию, причину и приоритет. Затем интерфейс показывает только следующий допустимый шаг: **Рассчитать влияние → Отправить на согласование → Technical Review → Выпустить ECO → Начать внедрение → Подтвердить внедрение**.

Если после impact analysis изменился чертёж, BOM, CAD или область влияния, система не даст выпустить ECO до повторной проверки.

## Качество и индустриализация (v4.1)

Внутри проекта появилась одна карточка **«Качество и индустриализация»**. Она специально свёрнута по умолчанию, чтобы не перегружать рабочий экран.

Сначала вы видите только:
- общий advisory score;
- APQP / Core Tools / PPAP / 8D;
- несколько пунктов, требующих внимания.

Если ваша задача относится к качеству, нажмите **«Открыть инструменты качества»**. Внутри доступны APQP, критические характеристики, PFMEA, Control Plan, PPAP и 8D. Выбранная сверху производственная зона применяется автоматически.

Если вы обычный инженер и качество не относится к вашей текущей задаче, карточку можно вообще не открывать.

## Готовность к SOP — v4.3

Внутри проекта есть одна карточка **«Готовность к SOP»**. Обычно достаточно посмотреть общий процент и блокеры. Нажимайте «Открыть готовность к запуску» только когда нужно добавить контрольный пункт или Run@Rate/Pilot/DV-PV.

Не нужно вручную повторять PPAP, 8D, ECR/ECO или состояние оснастки: сервис использует уже существующие данные проекта. Итоговый статус носит рекомендательный характер и не заменяет корпоративное решение о SOP.


## Требования и подтверждение — v4.4

В проекте появилась одна карточка **«Требования и подтверждение»**. Обычно её не нужно держать раскрытой: в закрытом состоянии она показывает общий процент, четыре показателя и несколько проблем.

Чтобы добавить требование: откройте карточку → «+ Добавить требование» → укажите код, текст, источник, деталь/систему и критерий приёмки. Затем добавьте verification.

Сервис не считает обычную галочку `Passed` доказательством. Нужен отчёт/документ, прошедший DV/PV/Run@Rate или approved Design Review. Если требование после испытания изменилось, старое подтверждение будет отмечено как **устаревшее**.

Матрица помогает доказать инженерную трассировку, но финальное соответствие OEM/регламентам подтверждается только утверждённым процессом компании.

## Поставщики и локализация — v4.5

В Project Workspace есть одна карточка **«Поставщики и локализация»**. Она свёрнута по умолчанию.

В закрытом виде показываются только Supplier Readiness, справочный Localization KPI, PPAP, входное качество и несколько главных проблем.

Важно: **100% локализации не означает, что поставщик готов**. Для готовности сервис отдельно проверяет технический пакет, RFQ, nomination, tooling, capacity/Run@Rate, PPAP, входное качество и 8D.

Чтобы начать работу, откройте карточку → `+ Добавить локализуемую деталь`. Для входного контроля используйте `+ Записать входное качество`.

Кнопка **Evidence Pack** фиксирует snapshot текущей готовности поставщика и связанных evidence для review/аудита.


## Стоимость и экономика — v4.6

В Project Workspace появилась одна сворачиваемая карточка **«Стоимость и экономика»**. В закрытом виде она показывает только текущую engineering cost на автомобиль, target, отклонение и годовой эффект.

Для подробного расчёта откройте карточку. Внутри доступны Baselines, стоимости деталей, supplier quotations и ECR/ECO impact.

Если используется material breakdown, задавайте массу, цену материала, scrap и conversion явно. Tooling не амортизируется автоматически: чтобы включить его в unit cost, нужно указать отдельный объём амортизации.

На карточке детали отображается только краткая economics-сводка.

Важно: стоимость **не меняет технический Release Readiness**. ERP/Finance остаются финансовым источником истины, а sourcing/investment decisions принимаются по корпоративному процессу.


## Архитектура и интерфейсы

Внутри проекта откройте карточку **«Архитектура автомобиля и интерфейсы»**. По умолчанию она свёрнута и показывает только число узлов, интерфейсов, подтверждённых сопряжений и первые проблемы.

1. Сначала создайте автомобиль/систему/подсистему/узел и при необходимости свяжите компонент с номером детали.
2. Добавьте интерфейс между двумя узлами: механический, электрический, fluid/gas, thermal, data/control или packaging.
3. Для критичных интерфейсов свяжите требование и verification evidence. Статус PASSED без evidence не считается подтверждением.
4. Если позже меняется интерфейс или сопряжённый узел, старое подтверждение становится устаревшим и требует review.
5. В карточке детали блок **«Влияние по интерфейсам»** показывает соседние узлы, требования и открытые ECR/ECO, которые может затронуть изменение.

Интерфейсная матрица помогает инженеру оценивать влияние, но не выпускает изделие автоматически.

## Варианты автомобиля

В проекте откройте карточку **«Варианты и конфигурации»**. Здесь можно создать вариант (рынок, двигатель, КПП, кузов, комплектация) и указать применимость детали.

- **Применяется** — деталь явно относится к варианту.
- **Не применяется** — деталь явно исключена.
- Если связь не задана, сервис показывает **«Не определено»** и не включает этот вариант автоматически.

В карточке детали и ECR/ECO есть короткая сводка затронутых вариантов.


## Релиз и версии BOM

В проекте откройте карточку **Релиз и версии BOM**. В обычном состоянии она показывает только количество baseline/BOM-версий и статус последнего snapshot. Для сравнения выберите две версии BOM и нажмите **Показать разницу** — система выведет только добавленные, удалённые, заменённые и изменённые позиции.

В карточке конкретной детали доступно такое же действие **Сравнить версии BOM**.

`Design Freeze` можно фиксировать как инженерный snapshot. `Release` и `SOP` требуют Engineering Admin. Даже чистый baseline не является автоматическим разрешением на выпуск.

## Engineering Program Control — v5.4

В Project Workspace появилась одна сворачиваемая карточка **Engineering Program Control · v5.4**. Она не заменяет корпоративный график проекта и не создаёт отдельный список задач.

Карточка показывает:

- следующий контролируемый gate (Design Freeze / Release / SOP);
- deterministic gate forecast GREEN / AMBER / RED;
- program maturity по Product, Program, V&V, Manufacturing/Launch, Supplier/PPAP, ECR/ECO, Quality и Risk;
- maturity по доступным производственным зонам;
- critical dependency chain между engineering milestones;
- top blockers и Engineering Command Brief;
- what-if сценарий: что произойдёт, если выбранный milestone сдвинется на N дней.

Чтобы связать два этапа, откройте `Настроить инженерную dependency`, выберите predecessor и successor, укажите lag в днях и criticality. Система не позволит создать цикл.

What-if симуляция **не меняет реальные даты**. Она только распространяет заданный сдвиг по dependency-графу и показывает downstream exposure.

Важно: displayed critical chain основан на due-date/dependency slack. Это не формальный CPM, пока authoritative program system не передаёт длительности/ресурсы. Gate forecast носит advisory характер и не утверждает Design Freeze/SOP автоматически.

## Configuration & Release Assurance — v5.5

В Project Workspace под Program Control находится одна сворачиваемая карточка **Configuration & Release Assurance · v5.5**.

1. Выберите вариант автомобиля; при необходимости укажите VIN/vehicle ID.
2. Нажмите **Проверить**. Сервис построит 100% конфигурацию только из явно включённых applicability rules. `UNKNOWN` никогда не считается применимым автоматически.
3. Проверьте **EBOM ↔ MBOM**. Отсутствующий MBOM отображается как `NOT_CONFIGURED`, а revision/quantity/position mismatch — как явный gap.
4. Откройте **AS-DESIGNED → AS-PLANNED → AS-BUILT** и убедитесь, что released design, manufacturing plan и фактически собранные данные не расходятся. Approved Engineering Deviation может явно разрешить AS-BUILT revision mismatch.
5. В **Effectivity / Cut-in / AS-BUILT** проверяйте plant/VIN/date effectivity, готовность смены ревизии, disposition старого остатка, logistics confirmation и PPAP.
6. **Variant / Plant Matrix** показывает конфигурационные gaps отдельно по доступным вариантам и заводам.
7. **Cross-system consistency** показывает read-only drift между PLM/PDM, ERP/manufacturing и MES/import.
8. **Release Package JSON** формирует evidence snapshot с SHA-256 fingerprint. Новый Release Baseline v3 фиксирует MBOM/effectivity/cut-in/supersession, поэтому реальные изменения после freeze попадают в Release Drift.
9. В **Ask Configuration** можно спросить, почему вариант нельзя передать на Pilot Build/SOP. Ответ детерминированный и CPU-only.

Engineering Admin может загружать контролируемые authority-shadow данные через защищённый API/интеграцию. UI намеренно не дублирует полноценные редакторы ERP/MES/PLM. Финальный manufacturing handover/release всегда подтверждает человек.

## Series Quality & Manufacturing Intelligence — v5.7

После SOP в Project Workspace появляется одна сворачиваемая карточка **Series Quality & Manufacturing Intelligence · v5.7**.

Она показывает только доступные пользователю факты серии:

- общий Series Health;
- defect rate;
- Cp/Cpk/Pp/Ppk и тренд capability;
- quality change-point signals;
- supplier-lot, station и shift investigation signals;
- containment progress;
- PFMEA ↔ Control Plan ↔ actual defect review;
- tooling/calibration review signals;
- field/warranty clusters;
- advisory Cost of Poor Quality.

`Change point`, `supplier lot`, `station` и `shift` — это **сигналы для расследования**, а не доказанная причина. Сервис всегда сохраняет `causal_claim=false`, пока root cause не подтверждён человеком по корпоративному процессу.

Для containment используйте VIN suspect-population API/интеграцию: популяция строится по фактической genealogy (part/revision/supplier/lot/plant/variant/date), а не по предположению. Engineering Admin может импортировать series/SPC/QMS shadow data через защищённые endpoints; интерфейс специально не превращён в копию MES/QMS.

Field/warranty случаи становятся доступными в Engineering Knowledge Memory только в рамках тех же Project/Area/Document ACL. COPQ носит справочный характер; ERP/Finance остаётся финансовым источником истины.
